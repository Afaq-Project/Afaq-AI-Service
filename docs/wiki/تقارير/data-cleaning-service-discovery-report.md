# Feature 3: تقرير استكشاف خدمة تنظيف البيانات

## موضع الخدمة في النظام

يعتمد النظام دورة بيانات من ثلاث مراحل: فحص الأمان (`src/modules/security/`)، ثم scraping والاستخراج (`src/modules/scraping/`)، ثم التنظيف والتوحيد (`src/modules/cleaning/`). تقع خدمة التنظيف بعد حفظ مخرجات scraping في Stage 2 وقبل حفظ بيانات الفرص المعيارية للنشر واستهلاكها في matching وعمليات embeddings. تتولى scraping حفظ المصدر ومحتوى الناشر؛ وتتولى cleaning التحويلات المعيارية.

## التدفق والواجهات الحالية

1. تستقبل API routes (`src/api/`) طلبات تشغيل scraping وتفوضها إلى services.
2. تنسق scraping اكتشاف المصادر والقوالب وعمليات الجمع. تُحفظ بطاقات Level 1 في `raw_listings`، بينما تُحفظ تفاصيل Level 2 والبيانات الوصفية في `raw_grant_details`.
3. يمثل `raw_grant_details.raw_payload` المدخل المنظم الخام، وترافقه معرّفات المصدر والقائمة والعملية، وبيانات اللغة، والتحقق من رابط التقديم، وبيانات المرفقات، والحالة، وحقول retry والأخطاء.
4. يحدد تقرير scraping أن التفاصيل الخام تبدأ بحالة `pending` وتكون جاهزة للتنظيف اللاحق. تقرأ خدمة التنظيف السجلات المؤهلة وتحولها إلى فرص معيارية منظمة لاستهلاكها من التخزين والنشر وخدمات AI matching.

يحدد سجل المعمارية المسار المقصود للوحدة (`src/modules/cleaning/`) ويصنفها كميزة مستقبلية. يضم مخطط Prisma الحالي وجدول بيانات Feature 2 جداول الاستخراج الخام، كما يحتوي المخطط الحالي على `CleanedOpportunity`. لكن لم يُعثر في المواد التي تمت مراجعتها على عقد موثق لوظيفة التنظيف أو لجدولة عملها وواجهات API الخاصة بها. هذه قرارات ينبغي تحديدها ضمن Feature 3.

## الاعتماديات والمستهلكون

**المدخلات والاعتماديات:** سجلات raw listing وraw detail ومعلومات مصدرها القادمة من scraping؛ والوصول إلى قاعدة البيانات عبر حدود application service/repository؛ واتفاقيات domain/config/error المشتركة. يمكن استخدام أدوات parsing وHTML القياسية و`nh3` الموصى بها معمارياً. لا تتضمن cleaning أي network أو DNS أو browser أو تنزيل ملفات خارجية. يجري التحقق الأمني من الروابط والتحقق من المرفقات في المراحل السابقة.

**المستهلكون اللاحقون:** تخزين الفرص المعيارية ونشرها، ثم AI matching وإنشاء vector embeddings. لا تحدد المواد التي تمت مراجعتها أسماء الوحدات أو عقود النشر وmatching وembeddings بدقة؛ لذا ينبغي لـ Feature 3 تحديد الواجهات المطلوبة دون افتراضها.

## المتطلبات والأهداف الأساسية

- تحويل الحقول المنظمة الخام إلى سجلات فرص معيارية ثابتة ذات أنواع واضحة، مع الاحتفاظ بمصدر السجل الخام وبيانات provenance.
- استخراج النصوص العادية من الحقول المنظمة، وفك HTML entities، وتطبيع Unicode باستخدام NFKC، وإزالة محارف التحكم غير القابلة للطباعة.
- تنظيف الأوصاف الغنية باستخدام قائمة سماح آمنة وصريحة عبر `nh3` عند الحاجة إلى إبقاء التنسيق.
- تحليل وتوحيد التواريخ بصيغة ISO 8601 وقيم العملة والتمويل وتصنيفات الدرجات الأكاديمية. كما يحدد سجل المعمارية رموز العملات ISO 4217 ورموز الدول ISO 3166-1 alpha-2.
- الحفاظ على تجميع السجلات ثنائية اللغة وبيانات اللغة، والتعامل مع القيم الناقصة أو غير الصالحة أو الملتبسة دون اختلاق معلومات؛ وتسجيل مشكلات كل حقل للمراجعة أو retry.
- جعل المعالجة قابلة للتكرار وidempotent، وتتبع حالات lifecycle مثل pending/processing/cleaned/failed مع الأخطاء، بما يتوافق مع اتفاقيات سجلات scraping. لا تزال atomicity وسياسة التعارض وretry بحاجة إلى عقد خاص بالميزة.
- وضع منطق التحويل في `src/modules/cleaning/services/*_service.py`، وحصر ملفات جذر الوحدة في models/exceptions/exports. تبقى إدارة قاعدة البيانات ضمن application services/repositories.
