# ADR 0003: مستودع مركزي لإدارة قاعدة البيانات المشتركة

- **الحالة:** مقبول
- **التاريخ:** 2026-11-15
- **صاحب القرار:** المستخدم
- **النطاق:** ملكية قاعدة البيانات ومخططها وmigrations لجميع الخدمات المستهلكة

## السياق

تتطور خدمات المشروع حالياً مقابل قواعد بيانات منفصلة، بينما يتطلب الشكل النهائي علاقات مرجعية حقيقية بين فرص الخدمة وجداول مرجعية مثل الدول والمدن والتخصصات. لا يدعم PostgreSQL إنشاء foreign keys بين قواعد بيانات مختلفة. كما أن وجود أكثر من Prisma migration stream على قاعدة مشتركة يسبب تاريخ تطبيق متعارضاً، ويعيد مخاطر ترتيب migrations والاعتماديات الدائرية.

كان الفصل بين قواعد البيانات إجراءً مؤقتاً لتقليل احتمال أن تكسر فرق التطوير مخططات بعضها أثناء التطوير. الخطة النهائية كانت دمجها بعد استقرار العمل. لا يمكن تنفيذ الدمج الحي حالياً دون تعريض بيئة الإنتاج للتوقف أو الاضطراب، لذا سيُطوّر النظام مقابل مخطط اختبار يعكس الشكل النهائي بعد الدمج.

## القرار

إنشاء مستودع مستقل مخصص حصرياً لإدارة قاعدة البيانات المشتركة. هذا المستودع ليس تطبيقاً؛ بل هو المصدر المرجعي والسلطة الوحيدة على المخطط والتغييرات التشغيلية لقاعدة البيانات.

يحتوي المستودع على:

- ملف `schema.prisma` canonical واحد.
- مجرى `migrations/` واحد ومرتب.
- reference-data seeds.
- أدوات Postgres المحلية.
- scripts للنسخ الاحتياطي والاستعادة واختبار الاستعادة.
- إعدادات CI لتطبيق migrations والتحقق منها ونشر Prisma Client package مولدة.

أي تغيير في قاعدة البيانات يتطلب pull request إلى مستودع قاعدة البيانات. تُطبق migrations حصرياً عبر CI الخاص به. تستخدم الخدمات الأخرى قاعدة البيانات كمستهلكة ولا تملك schema أو migrations مستقلة.

## الحدود والمسؤوليات

### مستودع قاعدة البيانات يملك حصرياً

- تعريف schema وجميع الجداول والعلاقات والقيود.
- كتابة وترتيب وتطبيق migrations.
- backups واختبارات restore.
- إدارة database roles والpermissions.
- reference data.
- نشر Prisma Client package المولدة.

### مستودعات الخدمات المستهلكة

- تستخدم Prisma Client المنشورة للتعامل مع البيانات.
- تستخدم credentials محدودة بصلاحيات DML.
- لا تحتوي على مجلد `migrations/` أو نسخة محلية من `schema.prisma`.
- لا تشغل `prisma migrate` ولا تتصل بقاعدة البيانات باستخدام DDL privileges.
- تمرر أي احتياج لتغيير schema عبر pull request إلى مستودع قاعدة البيانات.

## المبررات

- لا يمكن لعدة قواعد بيانات PostgreSQL أن تشترك في foreign keys عابرة لقواعد البيانات.
- وجود Prisma migration authority واحدة يمنع تعارض مجاري migrations.
- يضمن مجرى migrations واحداً ومرقماً ترتيب تطبيق موحداً.
- تمكّن قاعدة واحدة من إنشاء referential integrity حقيقية بين بيانات الفرص والجداول المرجعية المشتركة.
- يوضح الملكية ويفصل مسؤولية schema stewardship عن منطق الخدمات.
- تستطيع الخدمات إصدار تغييرات منطقية مستقلة عن تغييرات schema، كما يسهل إضافة خدمات مستهلكة جديدة.
- استخدام schema اختبار تمثل الشكل النهائي يتيح تطوير العلاقات المستهدفة دون إجراء دمج حي في الإنتاج الآن.

## البدائل التي جرى النظر فيها

### Prisma migrations مستقلة لكل خدمة على قاعدة مشتركة

**مستبعد:** وجود أكثر من migration authority على schema واحدة يخلق سجلات تطبيق متضاربة ومخاطر ترتيب واعتماديات يصعب تتبعها.

### إبقاء قواعد البيانات منفصلة مع نصوص بدلاً من العلاقات

**مستبعد:** يمنع أو يصعب فرض referential integrity باستخدام foreign keys، ويستمر بتكرار قيم مثل البلد والتخصص كنص حر.

### منح كل خدمة صلاحية DDL على قاعدة البيانات الموحدة

**مستبعد:** يعيد مخاطر تعديل الجداول المشتركة دون تاريخ migrations موحد أو ضمان ترتيب التغييرات.

### إبقاء الجداول منفصلة منطقياً بلا مستودع مركزي

**مستبعد:** لا يحل مشكلة مالك migration stream، ولا يلغي الحاجة إلى تنسيق cross-schema changes.

## النتائج

### الفوائد

- تسلسل migrations واضح ومركزي من خلال مجرى واحد.
- ملكية واحدة غير ملتبسة للمخطط وتطبيقه.
- foreign keys وعلاقات سليمة داخل قاعدة PostgreSQL واحدة.
- فصل واضح بين schema stewardship ومنطق التطبيق.
- نشر خدمات مستقل عند عدم الحاجة إلى schema changes.
- onboarding أبسط لخدمات جديدة كمستهلكة لقاعدة البيانات وPrisma Client.

### التكاليف والمقايضات

- كل schema change يتطلب pull request ومراجعة وإصدار Prisma Client package جديد.
- لا تستطيع فرق الخدمات إدارة schema أو migrations بنفسها.
- تقل حرية التجريب المستقل على schema؛ يجب توجيه التغييرات عبر المستودع المركزي.
- يصبح مستودع قاعدة البيانات وCI الخاص به مساراً إلزامياً لكل schema evolution.
- لا يجري دمج قواعد الإنتاج الآن؛ يجب بناء واختبار schema الهدف على قاعدة الاختبار ثم تخطيط cutover بعد اكتمال التطوير.

## طريقة التطوير والانتقال

- تعد قاعدة الاختبار مرجعاً مؤقتاً لاختبار schema الهدف بعد الدمج.
- تصمم خدمات الفرص مقابل الجداول المرجعية الموحدة، بعلاقاتها المحددة في canonical schema.
- لا تُجرى تغييرات على قاعدة الإنتاج الحية ضمن تطوير schema الهدف.
- بعد اكتمال تطوير الخدمات، يُخطط لدمج قواعد البيانات وترحيل البيانات واختبار الرجوع/الاستعادة قبل cutover.
- تُحل كل الاعتماديات وترتيبات إنشاء الجداول والقيود داخل migration stream المركزي؛ وعند وجود دورات FK، تُنشأ الجداول أولاً ثم تضاف القيود في خطوات لاحقة ضمن هذا المجرى.

## المراجع

- `docs/schema.prisma` — مخطط core backend الحالي ومصدر الجداول المرجعية المقصودة.
- `prisma/schema.prisma` — مخطط الخدمة الحالي الذي يعكس النموذج السابق.
- `prisma/migrations/` — migrations الحالية التي تحتاج مواءمة مع النموذج النهائي.
