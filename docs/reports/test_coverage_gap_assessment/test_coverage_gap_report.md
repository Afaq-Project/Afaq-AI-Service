# Test Coverage Gap Assessment: Specs 1 and 2

## Executive summary

The repository has substantial deterministic unit coverage for URL validation, file validation, schema validation, pagination, template matching, prioritization, language classification, and several orchestration workflows. The main weakness is integration confidence: most tests named “integration” use `FakePrisma`, mocked crawler/browser results, mocked LLM completions, and a mocked webhook client. They verify service composition against those fakes, but do not establish that the deployed dependencies behave the same way.

The supplied k6 report records 61/61 baseline checks and 40/40 burst checks passing, with no observed HTTP 500 responses. Those results are useful as a short API smoke/burst check. They do not verify most browser, database state-transition, LLM, document-storage, or webhook requirements. The 72.09% `http_req_failed` metric is largely expected 4xx traffic from negative scenarios; it is not an application failure rate.

**Testing conclusion:** treat the current suite as a good unit-test foundation and partial API/orchestration coverage. Add the production-like dependency-path scenarios below before claiming the critical security and scraping workflows have been verified end to end.

## 3. Specific errors and edge behaviors requiring stronger tests

| Error or edge | Gap | Scenario and expected invariant |
|---|---|---|
| **HTTP 429/503 during crawl** | `check_rate_limit` and Retry-After parsing have unit tests, but the source coordinator’s persisted cooldown and lock release are not verified end to end. | Return 429 and 503 with `Retry-After` values below, at, and above 300 seconds, including HTTP-date, malformed, and missing headers. Assert whether the source enters cooldown according to policy, the exact error code, no further crawl/LLM call, and lock release. |
| **Cloudflare/CAPTCHA challenge** | Challenge-token detection is unit tested; operation-level failure counting, cooldown, no AI call, and unlock are not jointly proven. | Return challenge HTML from the controlled browser fixture during onboarding and run. Assert `ERR_ACCESS_CHALLENGE_BLOCKED`, source cooldown/failure count, no discovery/template LLM invocation, terminated browser context, and no stuck lock. |
| **Failure cleanup on unexpected exceptions** | Happy paths, explicit timeout, and cancellation are tested, but failures at each phase boundary can leave state inconsistent. | Inject exceptions at source-config read, catalog crawl, listing save, detail extraction, document upload, status update, and webhook dispatch. For each, assert operation/source status, lock release, partial counts, error summary, and that subsequent runs are possible. |
| **SSRF via DNS/rebinding, redirect, and browser subrequest** | IP and redirect logic have negative tests, but browser DNS pinning is not integrated; attachment redirect tests focus on circular loops. | Test a safe initial host redirecting to loopback/metadata, a DNS answer changing after validation, and a page whose script requests a private IP hostname. Assert every hop/subrequest is blocked before reaching the private listener, with typed errors and no S3/LLM side effects. |
| **Malformed and failing download streams** | Magic bytes, 25 MB ceiling, zip-bomb, and cache scenarios exist, but end-to-end ingestion error states are not comprehensively verified. | Simulate 404/429/503, wrong `Content-Length`, content-length under-reporting, connection reset mid-stream, empty/truncated PDF, invalid DOCX central directory, checksum mismatch, and S3 upload failure. Assert correct error mapping, retries only where allowed, and no partial object/metadata. |
| **Selector/schema validation boundaries** | Static complexity constraints and mocked timeout path are covered; tests do not establish real parser behavior on representative hostile-but-valid selectors and malformed model outputs throughout template persistence. | Exercise selectors at the maximum allowed length/depth/combinator boundary and just beyond it; pass malformed JSON, missing required fields, unknown fields, invalid CSS, and a failing dry-run. | **HTTP/API error contracts** | k6 covers several common statuses, but not every documented endpoint error or response body. | Add endpoint tests for unknown source on run (404), bad query bounds/enums (422), operation/source malformed UUIDs, all-locked versus mixed locked/eligible batches, missing/invalid auth for every protected route, and exact error code/message envelope. ## 4. Test-writing guidelines

1. **Trace each requirement to a test.** Reference the Spec/FR/UC and identify the observable invariant. Keep a coverage matrix that distinguishes unit, dependency integration, API contract, and k6/load evidence.
2. **Use scenario-specific deterministic fixtures.** Prefer local HTTP fixtures, `httpx.MockTransport`, fake LLM responses, and isolated test database rows. Do not make routine tests depend on arbitrary public sites or live provider credentials.
3. **Test the right boundary.** Unit tests isolate algorithms; repository integration tests use PostgreSQL/Prisma; browser integration tests launch the real browser against local fixtures; API tests exercise the ASGI app; k6 tests send HTTP traffic to a running non-production app.
4. **Assert state transitions, not just status codes.** For async operations, follow the returned `operation_id` to a terminal state and verify counts, source state, persisted records, locks, errors, and cleanup. For reject paths, prove forbidden side effects did not occur.
5. **Make negative cases precise.** Assert the exact status and domain error code expected. Do not let a DNS failure count as a relevance rejection or accept a broad set of unrelated statuses.
6. **Seed and clean up explicit test data.** Never depend on hardcoded UUIDs existing. Use unique test IDs, a dedicated database/schema/bucket, and guaranteed cleanup. Do not trigger “all active sources” in shared environments unless every active source is test-only.
7. **Exercise concurrency deliberately.** Synchronize concurrent requests with barriers/events; assert one idempotent operation, one lock owner, correct conflict/skip behavior, no duplicate crawl, and eventual lock release. Test cross-process behavior where database locks are the coordination mechanism.
8. **Inject time and failures instead of waiting.** Use controllable clocks/events and transport fault injection for cooldowns, stale locks, timeout cancellation, and retries. Do not write assertions on test execution duration. The repository reserves performance/load thresholds for user-configured k6 tests.
9. **Do not confuse expected 4xx with service failure.** In k6, tag expected negative responses separately and define thresholds against unexpected failures. Checks should fail the run for violated assertions; include a threshold on failed checks or an explicit unexpected-error rate.
10. **Use Pact for endpoint contract stability.** Keep request/response examples for every route, verify route roster and response contract, and reconcile intentional contract changes explicitly. The current operation lookup Pact message differs from the implementation and must be resolved before relying on Pact as a gate.
11. **Keep test data and secrets safe.** Require credentials through environment variables; do not include fallback API keys or production URLs in test defaults. Use test-only sources and fixture pages.
12. **Preserve project guardrails.** Follow `AGENT.md` and the test plan. Do not modify architecture tests or quality-gate rules to make tests pass; fix the implementation or seek the user's explicit instruction when a rule change is required.

## Recommended order

1. Reconcile and run Pact against the current route responses; make the contract gate fail closed.
2. Add PostgreSQL/Prisma integration scenarios for idempotency races, source-lock races, API-key persistence, and DLQ state.
3. Add real Chromium tests against local fixture servers for DNS pinning, tabs, redirects, pagination, challenge handling, and cancellation/timeout cleanup.
4. Add S3-compatible storage and local webhook receiver integration tests.
5. Complete k6 scenarios for valid onboarding, operation polling to terminal state, true same-key concurrent retries, active abort, and controlled error responses.
6. Add deterministic fault-injection coverage for LLM, browser, repository, storage, and webhook failure branches.
